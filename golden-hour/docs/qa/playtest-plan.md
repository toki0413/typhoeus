# 玩法试玩与验收计划

> 目的：验证“5–8 分钟一局、10 人搜救、逐名确认、返回撤离”是否成立，并收集可执行的调参证据。
> 当前状态：自动化门禁已覆盖功能与性能；真人时长与难度仍需本计划验证。

---

## 1. 验收问题

1. 新玩家能否在无文字攻略的情况下，理解“带离 → 走到门口 → 确认送达”？
2. 一局实际时长是否落在 5–8 分钟？
3. 10 人规模是否过难、过拖，或空呼/确认环节造成挫败？
4. 桌面与移动端是否都能完成至少一个区域？
5. 失败是否可解释：玩家能否说出“为什么居民死了 / 为什么我倒了”？

---

## 2. 对象与分组

| 组别 | 人数 | 说明 |
| --- | --- | --- |
| 新玩家 | 5–8 | 没看过开发文档、没玩过原型 |
| 消防/安全背景 | 2–3 | 用于专业性判断 |
| 移动端 | 3–5 | 触屏 D-pad 与确认按钮 |

每轮 20–30 分钟：1 次自由探索 + 1 次复盘后重试。

---

## 3. 流程

1. 说明：这是原型，目标是救人并安全撤离；没有标准答案。
2. 第一次试玩：只看游戏内提示，不口头指导。
3. 观察记录：卡点、误解、放弃点、确认按钮是否被发现。
4. 复盘：展示结算页的星級、原因、曲线与动作条目，请玩家解释结果。
5. 第二次试玩：允许使用复盘信息，观察是否改进。
6. 结束访谈：3 个问题——哪里最困惑、哪里最紧张、还会不会再玩。

---

## 4. 采集指标

优先从 HUD 与本地诊断导出，避免手工抄写：

| 指标 | 来源 |
| --- | --- |
| 一局时长 | HUD“用时” |
| 救出 / 失去 / 区域完成 | HUD 居民行 |
| 评分、星级、失败原因 | 结算卡片 |
| 峰值暴露、错误灭火剂、空呼剩余 | 结算/诊断 run 摘要 |
| 确认送达次数与耗时 | 操作观察 + 动作复盘 |
| 页面错误 | `window.__ghDiag.snapshot()` |

导出方式（开发者控制台）：

```js
copy(JSON.stringify(window.__ghDiag.snapshot(), null, 2))
```

诊断只存本地 localStorage，不发送网络请求；不要在记录中写入姓名等个人信息。

---

## 5. 通过标准

| 指标 | 目标 |
| --- | --- |
| 中位时长 | 5–8 分钟 |
| 首轮完成至少 1 区 | ≥ 80% 玩家 |
| 首轮救出 ≥ 7 人 | ≥ 50% 玩家 |
| 第二轮救出 ≥ 7 人 | ≥ 75% 玩家 |
| 能解释“确认送达” | ≥ 80% 玩家 |
| 移动端完成 1 区 | ≥ 80% 玩家 |
| 严重卡点（无法继续） | 0 例 |
| 控制台未处理错误 | 0 例 |

未达标时的调参顺序：
1. 区域转移时间与路线长度。
2. 居民血量与烟热伤害。
3. 门口确认半径与提示强度。
4. 空呼消耗速度。
5. 最后才考虑减少区域/居民数量。

---

## 6. 观察清单

- 是否先找可见居民，还是直接冲向火源？
- 是否知道要“走回门口”？
- 是否在待确认期间继续深入，导致居民死亡？
- 是否理解区域条与“阶段”？
- 是否使用工具，还是忽略右侧面板？
- 移动端是否能同时控制方向与点击确认？
- 复盘后是否知道下一次该改什么？

---

## 7. 当前已知限制

- 没有远程遥测；数据需手动导出。
- 时长目标尚未由真人验证；模拟最优约 116.6 秒。
- 入口编排层仍较大，试玩中若出现回归，优先补 E2E 覆盖再修。
- 移动端只在无头浏览器做过 CSS/触控目标检查，需要真机复核。

---

## 8. 输出物

- 每轮一份匿名记录：玩家编号、组别、时长、救出数、卡点、原话摘录。
- 一份汇总：中位数、通过率、Top 5 问题、调参建议。
- 若通过标准未达成，回到调参顺序，不新增机制。
