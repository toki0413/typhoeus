# 作为插件，我们要什么功能，需要 AI 干什么

时间 2026-10-18。接 `AGENT_FORM_EVAL.md` 的骨架，把工具数从 6 更新到 8，并说清 AI 的确切任务。

---

## 一、我先说清我错在哪

我之前说"AI 只在边上，占代码 7.6%"。那是用 `import torch` 的行数在量 AI。

**那个数只说明"内核里没有神经网络"。而插件的 AI 在操作层，不在计算层。**

| 层 | 内容 | 用不用 ML |
|---|---|---|
| L4 **操作层（本插件的形态）** | 意图识别、工具编排、读数转译、拒绝 | **是 AI** |
| L3 编译层 | 8 份输出物的口径与结构 | 不用 |
| L1–L3 计算内核 | 守恒、下渗、能量、坡面流 | **刻意不用** |

**内核不用 ML 是纪律，不是落后。** 理由见第五节。

---

## 二、功能：8 个工具，一份输出物一个工具

不是把内核拆成几十个细粒度工具。**一份输出物一个工具**，因为用户的问题是"一份一份"问的。

| 工具 | 它替 Agent 回答的问题（值班员原话） |
|---|---|
| `get_preset_plan` | 汛前在哪布点、什么时候触发、按什么分级 |
| `get_recovery_order` | 灾后先修哪条路、比随机/按度基线好多少 |
| `get_event_reconciliation` | 这场损失怎么分解的、闭合不闭合、实测对得上吗 |
| `get_resilience_pricing` | 减少 1% 损失要多少工程投入 |
| `get_health_metrics` | 多少条指标通过、哪些不达标、哪些缺外部数据 |
| `get_health_report` | 一次全链跑下来守恒吗、结论是什么、数据有哪些 caveat |
| `get_multievent_calibration` | 跨场次标了什么、什么标不出来 |
| `get_flood_cards` | **这个点淹多少、这个读数能不能用**（带 trust 与 model_visible） |

**描述预算 963 / 2048 字节，47% 已用。** 这是为上下文窗口留余量，不是随手写短。

---

## 三、需要 AI 干什么：三件事

这三件事**内核干不了，人也干不动**。

### 任务一：跨输出物联合问答

8 份 JSON 是 8 个孤立文件。

用户会问：「今年布的那 12 个点，和恢复排序第 3 位，是不是同一批人？」

**这个问题跨了 3 份输出物。** 人要做交叉表；Agent 可以把它当同一个状态空间的 8 个投影来答。

### 任务二：口径自觉

同一场雨，两个口径差 **22.5 个百分点**（当前产物实测）：

| 口径 | 偏差 |
|---|---|
| 域内（1 站，集中在南部） | **−8.4%** |
| 全市（含北部暴雨中心余姚，官方 475 mm） | **−30.9%** |

**不给口径的数字就是误导。** 而人写报告时最容易把它漏掉。

Agent 的职责是：引用任何雨量或损失数字，必须同时带上口径。

**这条已经在工具层强制了**：`get_flood_cards` 的返回值里有 4 条读数规则，
其中一条是「引用任何 `model_depth_m` 时，必须同时引用该卡的 `trust` 与 `model_visible`」。

### 任务三：把读数翻成动作

「功能损失 0.412」这句话，值班员用不了。

他要的是：**哪些片区、多少人、多少台泵、什么时段。**

这个翻译原来的六份 JSON 完全没做。`cli decide` 开始做了（四个动作的余量表），
Agent 把它按用户的实际处境重新组织。

## 四、AI 不干什么（这是纪律）

| 不做 | 谁做 | 为什么 |
|---|---|---|
| 不调内核、不改参数 | — | **Agent 只能读 L3 编译输出**。允许它直接调 `kernel.run`，可追溯性就断了 |
| 不算水深 | 内核 | 可复算、可审计；模型会编数字 |
| 不判越域 | 护栏 R1 | 提示词约束不住模型，工具返回是确定性的 |
| 不给降级答案 | 护栏 | 降级答案在下游与真答案无法区分 |

护栏为什么在工具层而不在提示词层——`guardrails.py` 的原话：

> 规则放在这一层而不是提示词里，理由是提示词约束不住模型：
> 它可能照做也可能不照做，而工具返回是确定性的。

**三条规则：**
- **R1 越域拒绝**：余姚在域外且是暴雨中心，把域内结论套过去误差翻倍 → 拒绝，不降级
- **R2 弱基线拒绝**：排名必须附带评分口径，缺口径即拒
- **R3 单一口径拒绝**：涉及雨量或损失的数字必须双口径

## 五、为什么内核刻意不用 ML

**决策工具必须能解释、能复现。**

如果水深来自神经网络，我们无法回答规划局的问题：
「为什么 18 号点要加 0.12 倍排水？」

现在可以答：这一格排水只有全域一成，雨量到 340 毫米它就越过 15 厘米，
这组参数有复算指纹 `e464fea5962b`，你可以自己跑一遍。

**这是设计选择，而且是本产品在高风险应用一项上的优势。**
赛事评审对灾害类项目特别要求说明「模型误判与不确定性」与「安全边界」——
确定性内核让这件事能做，神经网络让这件事做不了。

---

## 六、所以"AI 必要"该怎么写

**不要写代码占比。写必要任务。**

> **AI 承担三个具体且必要的任务：**
> **① 跨 8 份输出物的联合问答**——人要做交叉表，且容易漏；
> **② 口径自觉**——域内 −8.4% 与全市 −30.9% 差 22.5 个百分点，漏了就是误导；
> **③ 把读数翻成可执行动作**——"损失 0.412" 到"哪些片区、多少人、几台泵"。
>
> **而"水深是多少"来自内核，不来自神经网络——
> 这是为了可复算与可审计，是高风险应用的必要设计。**

**三件事都可枚举、都可测**（`get_flood_cards` 的 4 条读数规则、
G16–G20 的五条 Agent 门槛、R1–R3 三条拒绝规则）。

---

## 七、一句话

> **这个插件的功能不是"让 AI 算水"，是"让 AI 敢用、会用、且说得清一个已经算好的模型"。**
>
> **前者是 ML 问题，后者是 AI 工程问题。我们做的是后者，而这恰是灾害类应用最先卡住的地方。**
