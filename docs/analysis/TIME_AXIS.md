# 时间轴：现状与改动（方案 A）

时间 2026-10-18。回答「把逐时雨换成亚小时，要动多少东西」。

## 现状

| 位置 | 事实 |
|---|---|
| `config.py` `L4.dt_s` | **600 s**，内核本来就是 10 分钟步长 |
| `rainsrc.fetch_era5` | 原来写死 `step_per_hour = 6`、`nt = 72*3600/600`、`dt_h = 600/3600` |
| `rainsrc` 标定段 | 原来写死 `step_per_hour = 6`、`dt_h = 600/3600` |
| `kernel.run` | 时间循环按 `cfg.dt_s` 推进，本身与输入分辨率无关 |

结论：**求解器不用改；卡住的是「逐时输入怎么铺到 10 分钟时间轴上」**，而原来只是把每小时重复 6 次。

## 本次改动（方案 A：参数化，不改默认）

1. `fetch_era5(grid, ..., dt_s=600.0)`：步数、步长由 `dt_s` 推导，不再写死；
2. `get_rainfall(..., dt_s=600.0)`：透传；缓存名在非 600 s 时追加 `_dt{秒}`，避免 10 分钟的场被当 15 分钟用；
3. 标定段由场长度反推 `step_per_hour` 与 `dt_h`（`长度 = 72h/dt + 1`）；
4. CLI 新增 `--dt-seconds`，只在显式传入时改 `cfg.l4.dt_s`；
5. 默认 600 s：155 条测试全过，产物与既有指纹一致。

用法：

```bash
python -m typhoeus.cli run --dt-seconds 900
```

## 未验证

- **15 分钟路径没有端到端跑过**：非 600 s 需要重新拉 ERA5（本机无外网），本机也没有 `_dt900` 缓存；
- 步长变大要重新验 CFL 与守恒残差；步长变小（300 s）会让 `nt` 翻倍、内核耗时约翻倍；
- 改 `dt_s` 会改变 `config_hash`，已发布的 `e464fea5962b` 与全部文档数字随之作废——这是方案 B 的成本，不是本次改动引入的。

## 真正的瓶颈

把逐时雨等分成 10 分钟，与现在的重复 6 次等价，**不产生新信息**。要提升「什么时候」，只能接真实亚小时数据：

| 数据 | 分辨率 | 前置 |
|---|---|---|
| 雷达 QPE | 6 分钟 | 气象部门授权 |
| 自动站 | 5 分钟 | 数据申请 |
| IMERG | 30 分钟 | `tools/imerg_fetch.py` 已有，需外网 |

有了序列之后，把 `dt_s` 设成对应分辨率即可，代码侧已经不需要再改。
