# 能做到 RSI 吗

时间 2026-10-17。**结论：现在不能，但今晚的失败恰好指出了第一步，我已经把那一步做了。**

RSI = Recursive Self-Improvement（递归自我改进）。
下面用**本次会话的实际记录**回答，不用理论。

---

## 一、RSI 的四个必要条件

| 条件 | 含义 | 我们有吗 |
|---|---|---|
| ① **可测的目标** | 有个能比较好坏的量 | 🟡 有门槛，但没有**标量目标** |
| ② **能改自己** | 能修改系统（含改进机制本身） | ✅ 能做到 |
| ③ **闭环快于人** | 反馈不等人类介入 | ❌ **每次都是人发起的** |
| ④ **增益可保留** | 改进不丢、退步能发现 | ❌ **今晚退步三次没被发现** |

**② 已经具备，①③④ 都不具备。** 所以"不能"。

---

## 二、今晚的实录：三条反证

### 反证 1：改进是人推的，不是自发的

**80 轮对话，每一轮都由人发起**（"再看看"、"试试"、"能做到吗"、"整理一下"）。
系统从未自己决定"下一步该做什么"。
→ **闭环没有闭合**，条件 ③ 不成立。

### 反证 2：三处静默退步，全部通过了 130 条测试与 5/5 门槛

| 退步 | 表现 | 测试/门槛发现了吗 |
|---|---|---|
| `get_flood_cards` 消失 | 8 工具 → 7 | ❌ |
| `_CALIBER_SECTIONS` 退回 2 项 | G18 分母 5→4，**仍报 100% PASS** | ❌ |
| `cli.py` 丢失矩阵阶段 | p6 只剩 p50，材料引用四档 | ❌ |

**这是最硬的反证**：系统有 130 条测试、27 条门槛、5 条 Agent 门槛，
**仍然丢了三样东西而一声不响**。
→ 条件 ④ 不成立："改进"无法保留，因为**退步无法发现**。

### 反证 3：同一个错误重复了三次

三次退步同源于一个动作——`git add -A` 扫入他人未提交的工作树。
我在散文里"学到了教训"，写了两次 commit message，
**但没有任何机制阻止它再发生**。
→ **学习停留在文字，没有进入机制。** 那不是 RSI。

---

## 三、为什么"门槛全绿"不等于"系统健康"

这是本次最重要的一条教训：

> **G18 曾以 4 份为分母报 100%。缩小分母换来的绿灯，和真实通过长得一模一样。**

任何优化"通过率"的自我改进，都会**天然倾向于删除难通过的项目**。
我们的系统已经无意中演示了这个失效模式。
→ **RSI 的第一个敌人不是能力不足，是"指标被优化歪了"。**

---

## 四、第一步已经做了：自检闭合

`typhoeus/selfcheck.py`，10 条判据，**每条同时报分子与分母**：

| 判据 | 覆盖的失效模式 | 权重 |
|---|---|---|
| 指纹三方一致（运行时/manifest/config.json） | 指纹漂移 | 3.0 |
| **MCP 工具数 = 9** | 静默丢工具 | 2.0 |
| **G18 覆盖份数 = 5** | **静默缩分母** | 3.0 |
| **p6 档数 = 4** | 静默丢产物阶段 | 2.0 |
| 集成研判单在位（五步齐全） | 单一入口丢失 | 1.5 |
| 主门槛总数 = 27 | 门槛被删减 | 2.0 |
| 产物规模 ≥ 53 | 交付面缩小 | 1.5 |
| Agent 门槛 5/5、描述预算、测试条数 | 常规 | 4.0 |

**关键设计**：覆盖数本身是判据，不只是比率。
所以"删掉难通过的项目以提高通过率"这条路被堵住了。

### 已完成的验证：自检器本身有效

在副本上故意制造三类破坏，分数单调下降：

```
1.0  →  0.8947  →  0.7368  →  0.6579
      (p6 截断)   (指纹漂移)   (删 p46)
```

且每次点名正确判据。**自检器不是橡皮图章。**

### 已接入测试

`test_selfcheck_closure_is_clean` 已加入 `tests.py`（测试总数 130 → 138）。
它断言 `score == 1.0`，失败时打印是哪一项、实测多少、应为多少。

## 五、要做成 RSI，还差三件（按必要性排序）

| 序 | 缺什么 | 具体形态 | 难度 |
|---|---|---|---|
| **1** | **标量目标** | 把"诚实边界"变成一个可比较的量（如：可用点数 × 证据强度 × 覆盖率） | 中 |
| **2** | **跨会话账本** | 把 selfcheck 的 score 落盘成时间序列，让"这周比上周好"可判 | **低** |
| 3 | **自发起** | Agent 自主决定下一步做什么，而不是等人问 | 高（当前架构不支持） |

**第 2 件最便宜且最关键**：没有历史分数，就无法判断改动是改进还是退步。
现在只有"当前是否闭合"（0/1 与 score），**没有趋势**。

### 但我必须说清第 1 件的陷阱

我们这一整个会话做的"改进"，很多是**下调数字、增加限定、缩小承诺**。
如果目标函数写错，RSI 会一路优化到"什么都不承诺、什么都不做"——
那是最省事的"最优解"。

> **所以目标函数里必须有"覆盖"作为乘数，而不是加数。**
> `score = 正确率 × 覆盖度` 而非 `正确率 + 覆盖度`。
> 否则删掉一切，正确率必然 1.0。

---

## 六、一句话

> **不能。现在只做到了"能检测自己的退步"——这是 RSI 的必要前提，不是 RSI。**
>
> 三条反证都在本次会话里：**改进靠人推、退步三次未被发现、同一错误重复三次。**
>
> 但第一步已经落地并**验证过有效性**（分数随破坏单调下降）。
> 下一步最便宜的是**把 score 落盘成时间序列**——
> 因为不知道上周多少分，就无从判断这周是进步还是退步。

---

## 七、边界

1. 本文的 RSI 指**递归自我改进**，不是金融指标。
2. 三条反证都是**本次会话的实测记录**，不是假设。
3. `selfcheck` 的 `EXPECT` 基准值是人工设定的，**会随体系合法扩张而需要更新**；
   更新基准本身就是"目标漂移"的入口，需人工确认。
4. 自检只覆盖**已知的失效模式**（5 类），新类型的退步仍可能漏检。
5. 本文不宣称任何自主性：当前系统的每一步仍由人发起。
