# 突破口：除了分析和展示，还能做什么

时间 2026-10-17。回答一个战略问题：**分析方法已经做到头了，还有什么别类的东西能改变局面？**

本文的核心发现来自两条政府公开通报，并用一个实验做了验证。

---

## 一、最重要的发现：官方已有一套 149 点的实时监测网

**宁波市大数据局 + 市水利局**在 2021 烟花期间上线了「台风积水地图」：

| 项 | 内容 |
|---|---|
| 监测点 | **149 个**（易涝低洼小区、路段、下穿立交） |
| 分档 | **红 ≥0.5 m / 橙 0.2 m / 黄 0.1 m** |
| 更新 | 物联网感知设备，**实时** |
| 内容 | 积水深度 + **水深变化曲线图** |
| 载体 | 「浙里办」宁波城市频道，25 日上午上架，单日访问 +1.4 万 |
| 扩展 | 余姚 48 点增量集成；26 日再上「河网水位」应用 |

来源：
- [宁波市大数据局：浙里办上线台风积水地图](http://dsjj.ningbo.gov.cn/art/2021/7/27/art_1229050878_58939528.html)
- [光明日报：「烟花」来袭，宁波首度打造数字孪生积水地图](http://dsjj.ningbo.gov.cn/art/2021/7/28/art_1229053029_58939532.html)

### 这与本项目的关系：**那 149 个"synthetic"点，对应的是这套真实系统**

仓库里的 `data/seed/monitor_sites_synthetic.json` 恰好是 **149 条**，
标为 `provenance=synthetic(布设逻辑占位)`。

**必须纠正一个说法**：这 149 个点**不是凭空编的**——
它们是**真实存在的官方监测网**，只有坐标与时序不公开，所以本项目用合成值占位。

> 「149 个监测点坐标是占位」≠「没有这 149 个监测点」。

## 二、这改变了产品定义：不竞争"算得准"，做"从观测量外推"

| | 官方已有 | 本产品可补 |
|---|---|---|
| 时间 | **现在**（实时） | **未来 72 h 情景**（p50/p80/p90/p95） |
| 空间 | 149 个点 | **点到面**（场） |
| 内容 | 水深 + 变化曲线（历史） | **越阈时刻与提前量** |
| 情景 | 单一实况 | **"雨再加 30% 会怎样"** |

**产品定位从「淹没计算器」变成「情景外推层」**——嵌在官方监测之上，不与它竞争。

这也回答了本项目一直被问的问题：**比赛说的"数据与协作支持"落在谁身上？**
——**宁波市大数据局（数字孪生积水地图）+ 市水利局（河网水位）**，
路径是具体可写的，不是空话。

## 三、但实验给出了一个必须接受的限制（`typhoeus/assimilation.py` → p26）

**假设**：若用观测插值代替模型模板，点位精度会大幅改善。

**做法**：留一法（LOOCV），用其余 16 点 IDW 插值被留出的 1 点，
并与模型、留一均值、全域常数三个基线比较。

### 结果

| 基线 | MAE |
|---|---|
| 模型 | **0.3593 m** |
| 留一均值（无空间信息） | 0.1029 m |
| **全域常数（0.396 m）** | **0.0968 m** ← 最优 |
| 最优 IDW（幂 1，无半径） | 0.1054 m |

### 判定：**IDW 优于模型，但输给一个常数**

```
IDW 0.1054  >  全域常数 0.0968     ← IDW 输
IDW 0.1054  >  留一均值 0.1029     ← IDW 输
```

**这意味着 17 个点的观测之间没有可用空间结构**（否则空间加权的 IDW 应优于常数）。
观测值分布：min 0.20 / max 0.64 / 均值 0.396 / 标准差 0.116——全挤在一个窄带里。

### 所以接观测的真实收益是

| 收益 | 数值 | 判定 |
|---|---|---|
| **校正系统性偏低** | MAE 0.359 → **0.097**（3.7 倍） | ✅ **真实且重要** |
| 改善空间格局 | IDW 赢不了常数 | ❌ **不成立** |

> **接观测能修「模型一律偏浅」，不能修「模型空间格局错」。**

这是本件最有价值的判断，因为它防止了一个过于乐观的产品承诺。

## 四、其余三个突破口（按性价比排序）

### B. 从「预测」转向「诊断」（反问题）

有观测 + 模型，可以反推：**给定这里的积水，哪段管网的排水能力不足？**
反问题通常比正问题容易做对，且管网诊断是**真实的采购需求**（设计院、水务公司）。
已有基础：p21/p22 已经实现了排水能力与降雨的反解。

### C. 第二场事件复现（证明可迁移）

`cli multievent` 已有 18 场历史气旋的批量框架。
跑通第二场事件（如 2013 菲特）比再增加一份本事件的分析更能说明"成熟度"。

### D. 交互式单页（让评委自己动手）

把 p6 情景矩阵做成带滑块的单页 HTML：拖雨量 → 看四色面积、可执行动作、
归因分型随之变化。**这是"展示"，但是交互式的，与静态报告不是一回事。**

## 五、我的判断

| 方向 | 2 天内可做 | 改变性质 | 建议 |
|---|---|---|---|
| **A. 对接 149 点观测（做偏差校正 + 外推）** | 接口可做，真数据需合作 | ⭐⭐⭐ 改变产品定义 | ✅ **写进方案作为核心路径** |
| B. 诊断型反问题 | 可做（已有反解底座） | ⭐⭐ | 🟡 次优先 |
| C. 第二场事件 | 可做（框架已存在） | ⭐⭐ 证明成熟度 | 🟡 次优先 |

| ❌ 再加分析 | — | 无 | ❌ 停止 |

**核心判断**：

> 本项目缺的从来不是"更准的模型"，而是**观测的接入点**。
> 149 个官方监测点已经存在，产品该做的是**站在它们上面做外推**，
> 而不是在没有观测的地方硬算——后者已经被 p4/p11/p25 反复证明走不通。

## 六、诚实边界

1. 149 点的**数据本身未取得**，本件的实验用的是项目内 17 个通报点。
2. 「接观测能校正偏低」在 17 点上是成立的，**外推到 149 点需重做**。
3. 官方三色分档（0.1/0.2/0.5 m）与本项目四色分级（0.1/0.2/0.5 m）阈值几乎一致，
   但**分级依据与业务含义需与官方核对**，不能默认等同。
4. 合作方身份来自公开通报，**未取得任何合作意向**——写进方案须标为"拟对接"，不是"已合作"。
